# 需求挖掘与通用设计规范

## 第一部分：需求挖掘

### 1. 上位机需求的特殊性

上位机项目的需求文档写得好的少，原因是客户只描述"要什么界面"，而不说"为什么要"。

**你的任务**：把客户的语言翻译成可实现的工程需求，并补全客户想不到的部分。

### 2. 需求挖掘提问清单

#### 2.1 背景类（先搞清楚现在怎么做的）

- [ ] 这套设备/产线现在是怎么运作的？人工还是已有系统？
- [ ] 现在记录数据用什么方式？（纸质、Excel、老软件）
- [ ] 新系统要替代什么？还是新增功能？
- [ ] 谁用这套系统？（操作工、工艺员、质量、设备维护）
- [ ] 一天用几次？连续用多久？
- [ ] 最头疼的问题是什么？

#### 2.2 功能类（用他们的语言问）

- [ ] 你希望打开软件第一眼看到什么？
- [ ] 操作员的典型一天是怎样的？从上班到下班做哪些操作？
- [ ] 哪些操作是每天必做的？哪些是偶尔的？
- [ ] 出问题时你希望软件怎么提示你？
- [ ] 有没有"出错了要能查出来是谁干的"这种要求？
- [ ] 数据要给别人看吗？给谁看？怎么给？

#### 2.3 硬件类

- [ ] 有哪些设备？型号是什么？有多老？
- [ ] 设备手册/通信协议有吗？在哪？
- [ ] 这些设备是谁装的？有问题找谁？
- [ ] 有没有设备是"不能停"的？

#### 2.4 现场类

- [ ] 电脑放在哪？操作员站着还是坐着？
- [ ] 环境怎样？（噪音、油污、温度、是否有手套）
- [ ] 屏幕多大？离操作员多远？
- [ ] 网络环境？（有没有网、能不能上外网）
- [ ] 谁来维护这台电脑？（本厂 IT 还是外部）

#### 2.5 数据类

- [ ] 数据要存多久？（常听到"永久"，需要追问"政策/审计有要求吗"）
- [ ] 数据要给谁？（质量部？客户？监管部门）
- [ ] 需要出报表吗？什么格式？
- [ ] 数据要上传到别的系统吗？（MES/ERP/QMS）
- [ ] 数据丢了会怎样？

#### 2.6 交付类

- [ ] 什么时候要？有没有节点（如客户验厂）？
- [ ] 谁来验收？按什么标准验收？
- [ ] 需要培训吗？培训谁？
- [ ] 上线后有问题找谁？保修多久？
- [ ] 以后加功能还要不要我们做？

### 3. 需求的三个层次

| 层次 | 客户说的 | 实际需求 | 你要做的 |
|---|---|---|---|
| 表层 | "要实时显示温度" | 需要一个数值显示 | 直接实现 |
| 中层 | "温度超了要报警" | 需要阈值判断 + 报警 + 记录 + 确认 | 追问阈值、分级、确认流程、是否需上传 |
| 深层 | "我要保证产品合格" | 需要完整的质量控制闭环 | 挖掘出 SPC、追溯、判定规则、SPC 图表 |

**方法论**：永远追问三层"为什么"。

### 4. 需求文档化的注意事项

- 每条需求必须**可验证**。禁止写"界面友好"、"响应快"、"稳定可靠"。
  - ✅ "界面响应时间 ≤ 200ms（点击到界面反馈）"
  - ✅ "连续运行 72 小时无异常退出"
- 必须区分**必须 / 重要 / 期望**三级。
- 必须明确**不做什么**（边界）。
- 不确定的必须标 ⚠️ 并列入待确认表。
- 量的表述必须带单位与精度。

### 5. 需求陷阱

| 陷阱 | 表现 | 应对 |
|---|---|---|
| 隐含需求 | "就是显示数据" → 其实要自动判定、SPC、上传 | 追问完整工作流 |
| 需求蔓延 | 开发中不断加需求 | 书面变更流程 + 影响评估 |
| 伪需求 | "要能手机看"（实际从不用） | 追问使用场景与频率 |
| 矛盾需求 | "数据永久保存" + "硬盘只有 120G" | 给出容量估算让他选 |
| 无法验证 | "要好用" | 转化为具体指标 |
| 甩锅需求 | "必须保证不出错" | 明确故障率与容错边界 |
| 时间倒逼 | "下周要" | 拆解为可交付的最小闭环 |

## 第二部分：通用设计规范

### 6. 上位机项目常见形态（帮助快速定位架构）

| 形态 | 特征 | 架构重点 |
|---|---|---|
| **监控型（HMI）** | 显示状态 + 少量控制 | 实时刷新、报警、曲线 |
| **采集型（DAQ）** | 高速采集 + 存储 | 吞吐、缓冲、落库管道 |
| **测试台型** | 控制仪器 + 判定 + 报告 | 流程编排、仪器抽象、追溯 |
| **控制型（SCADA）** | 下发指令 + 联锁 | 安全、状态机、权限 |
| **网关型** | 协议转换 + 转发 | 多协议、并发、缓冲 |
| **配置型** | 参数读写 + 备份恢复 | 校验、确认、版本 |

一个项目常是多种形态的组合。设计时按形态拆分模块。

### 7. 需求到设计的映射

```
需求类型           →  设计产出
─────────────────────────────────────────────
数据采集           →  通信层 + 采集调度 + 缓冲
数据展示           →  UI 模块 + 降采样 + 刷新策略
数据存储           →  存储层 + 批量管道 + 保留策略
控制下发           →  命令层 + 校验 + 确认 + 联锁
报警               →  规则引擎 + 通知 + 记录
权限               →  认证 + 授权矩阵 + 审计日志
报表               →  查询 + 模板 + 导出
对外接口           →  API/文件/数据库 + 重试补传
追溯               →  台账 + 版本记录 + 关联关系
```

### 9. 通用设计决策原则

| 决策点 | 默认选择 | 何时改为其他 |
|---|---|---|
| UI 框架 | WinForms | 需要复杂动效/矢量图形 → WPF |
| 目标框架 | .NET Framework 4.8 | 客户环境允许且需新特性 → .NET 8 |
| 数据库 | SQLite | 多客户端/大数据量 → SQL Server |
| 通信抽象 | 三层接口 | 单设备单协议且短期不扩展 → 可简化 |
| DI 容器 | Microsoft.Extensions.DI | 极小项目 → 手工组合 |
| 日志 | NLog | 需要结构化日志 → Serilog |
| 曲线 | 自绘 | 点数少且需交互 → 第三方库 |
| 数据刷新 | Timer 批量 | 低频（<1Hz）→ 数据到达即刷新 |
| 配置格式 | JSON | 需要注释 → XML/YAML |
| 部署 | 安装包 | 免安装需求 → 绿色包 |

### 10. 项目风险识别清单

| 风险类别 | 典型风险 | 早期信号 | 应对 |
|---|---|---|---|
| 硬件 | 设备到货延迟 | 采购未下单 | 打桩开发 + 仿真器 |
| 协议 | 手册不全/有误 | 手册缺寄存器表 | 提前实测抓包 |
| 环境 | 现场干扰严重 | 现场有变频器 | 提前准备隔离器 |
| 需求 | 需求不清/变更 | 客户说不清 | 书面确认 + 变更流程 |
| 性能 | 采样率达不到 | 单次耗时超预期 | 早期做性能验证 |
| 人力 | 关键人离开 | — | 文档化 + 代码规范 |
| 时间 | 节点压缩 | — | 拆最小闭环 |
| 集成 | 与下位机/MES 对不上 | 接口未定义 | 提前联调接口 |
| 部署 | 客户环境不符 | 未确认 OS/权限 | 提前现场勘查 |

### 11. 沟通规范

**与客户**：
- 需求确认要书面（邮件/文档签字），不要口头
- 变更必须评估影响并书面确认
- 定期同步进度，问题早暴露

**与下位机工程师**：
- 协议文档双方签字
- 字节序、地址表示法必须实测验证
- 异常码定义必须明确
- 联调前先各自单测

**与电气工程师**：
- 硬件核对表逐项确认签字
- 端口号、地址、波特率现场核对
- 线缆、接地方案确认

**团队内部**：
- 进度日志每轮更新
- 问题台账共享
- 关键决策记录理由
