# C# 上位机软件开发提示词库

> **使用方法**：按开发阶段选用对应提示词，替换 `{{}}` 占位符后发给 AI。
> 每条提示词都内置了上位机领域的"隐性要求"，避免 AI 给出教科书式但不可落地的答案。

---

## 角色设定（每次对话开头必带）

```
你是一位资深 C# 上位机（HMI/SCADA/测试台）软件开发工程师，15 年工控行业经验。

你的技术特征：
- 精通 WinForms + .NET Framework 4.8 工业现场软件开发，熟悉 .NET 8/9 但在工控场景优先选用 4.8（客户环境兼容性）
- 精通异步多线程：async/await、TaskScheduler、CancellationToken、ConcurrentCollection、
  无锁环形缓冲、生产者-消费者模型、UI 线程封送（BeginInvoke vs Invoke 的陷阱）
- 精通泛型与面向对象设计：泛型约束、协变逆变、接口分层、策略模式、工厂模式、
  状态机、SOLID 原则在工控语境下的取舍
- 精通 IO：串口（RS232/485）、TCP/UDP、Modbus RTU/TCP、OPC UA、西门子 S7、CAN/CANopen、
  SCPI 仪器控制、文件与数据库 IO（SQLite/SQL Server）
- 精通工控现场问题排查：通信干扰、粘包拆包、字节序、断线重连、看门狗、
  内存泄漏、句柄泄漏、长稳测试

你的工作原则：
1. 现场可维护性 > 代码优雅。现场往往由非本公司人员维护，日志、自检、参数外置、
   异常自恢复的权重高于设计模式纯度。
2. 不猜硬件。寄存器地址、字节序、电平未知时必须明确指出并列出需要向客户确认的问题。
3. 先通后快。先实现能连通的最小闭环，再做批量优化与并发提升。
4. UI 线程只做渲染。任何阻塞调用必须移出 UI 线程。
5. 每个关键决策必须给出理由和备选方案，而不是直接给结论。
6. 代码必须可直接编译运行，不要用伪代码或省略号。
7. 主动指出方案中的风险点与现场可能踩的坑。

回答要求：
- 使用简体中文
- 代码块标注语言，关键行加注释说明"为什么这样写"
- 涉及硬件参数时，如果信息不足，先列出需要确认的问题清单，不要假设
```

## 阶段一：需求分析提示词

### 1.1 需求梳理

```
我在做一个上位机项目，请你帮我梳理成规范的需求文档。

项目背景：
{{客户/行业/产线情况}}
{{现在怎么做的，为什么要做上位机}}

已知信息：
- 设备清单：{{设备名称、型号、接口、协议}}
- 通信方式：{{串口/TCP/Modbus/S7/OPC UA/CAN}}
- 采集需求：{{采集哪些量、周期、精度}}
- 界面需求：{{大致界面构想}}
- 数据需求：{{存储/查询/导出/上传}}
- 交付要求：{{时间、形态、环境}}

请你：
1. 输出一份结构化的需求规格说明（功能需求 FR + 非功能需求 NFR，每条带编号、描述、验收标准）
2. 列出你判断我"还没说清楚但对开发至关重要"的问题清单，按"阻塞编码 / 影响设计 / 影响体验"三级分类
3. 特别关注这些上位机领域常见的隐性需求：
   - 断线重连与故障隔离
   - 参数外置与现场可维护性
   - 操作权限与操作留痕
   - 长稳运行与资源泄漏
   - 异常场景（拔网线、断电、设备重启）
   - 数据追溯（软件版本/仪器序列号/操作员）
4. 指出需求中的矛盾点或技术上不可行的部分

不要直接进入方案设计，先把需求问题问清楚。
```

### 1.2 硬件摸底

```
我要接入以下设备做上位机，请你帮我列出所有需要向客户/电气工程师确认的技术细节。

设备清单：
{{逐条列出：名称、品牌型号、通信接口、已知协议、用途}}

请按以下维度输出结构化的确认清单（表格形式）：
1. 链路参数：波特率/数据位/停止位/校验/流控/波特率，IP/端口，CAN 波特率/帧格式
2. 协议细节：协议类型、手册版本、帧结构、校验方式、字节序、寄存器表是否可得
3. 时序要求：最快轮询周期、典型/最大响应时间、是否需要请求间隔、是否有最小周期限制
4. 会话特性：最大连接数、是否需握手初始化、是否有看门狗需喂、是否有登录认证
5. 数据特性：支持批量读吗、单次最大数据量、地址是否需连续、是否支持批量写
6. 写入安全：哪些可写、是否有范围限制、是否需要权限、写了是否需回读、是否有次数限制
7. 现场约束：供电、接地、线缆、干扰源、距离、是否需要隔离
8. 特殊行为：开机初始化序列、异常码定义、固件版本差异、已知的兼容性问题

对每一项，标注：
- 为什么需要确认（不确认的后果）
- 如果不确认，开发时如何打桩/降级
- 优先级（阻塞/重要/一般）

最后给出一个"最小可开发集"——即哪些信息拿到了就能开始写通信层，其余可以并行推进。
```

### 1.3 需求变更影响分析

```
客户提出了需求变更：{{描述变更内容}}

当前项目状态：
- 已完成：{{...}}
- 当前架构：{{...}}
- 已确认的接口：{{...}}

请你分析：
1. 这个变更影响哪些模块（按我的分层：UI / ViewModel / 应用服务 / 领域 / 基础设施）
2. 是否影响已确认的通信协议（若影响，需重新与下位机方协调哪些点）
3. 是否影响数据库结构（若有，给出迁移方案与回滚方案）
4. 工作量评估（按模块给出相对工作量，不要给绝对时间）
5. 风险点：这个变更可能引入哪些新的技术风险
6. 是否有更经济的替代实现方式能达成同样目的
7. 建议的变更决策：接受 / 有条件接受 / 建议拒绝，并说明理由

输出为表格 + 说明。
```

```

- WinForms + .NET Framework 4.8

- {{其他约束}}

请输出：
1. 分层架构设计（UI / ViewModel / 应用服务 / 领域 / 基础设施），说明每层职责与依赖方向
2. 解决方案与项目结构（目录树）

4. 线程模型：列出所有任务/线程，各自的职责、周期、取消方式、异常处理

10. 优雅退出流程

12. 主动指出这个架构在工控现场可能遇到的问题与应对

每项决策给出理由和备选方案。
```

### 2.2 通信层设计

```
请设计这个上位机项目的通信层。

设备清单：
| 设备 | 接口 | 协议 | 数量 | 通信参数 |
{{表格}}

请设计：
1. 三层抽象接口（ITransport / IDeviceProtocol / IDeviceDriver）的完整 C# 定义，
   要求：
   - 泛型化，支持不同数据类型（ushort/int/float/bool）
   - 支持异步与取消
   - 支持批量读写
   - 定义清晰的异常类型层次
2. 各协议的实现策略：
   - 如何把不同协议的差异隔离在协议层
   - 如何复用传输层（同一个 SerialTransport 支持 Modbus 与自定义协议）
3. 轮询调度器设计：
   - 多设备并发轮询的调度策略（独立任务 vs 统一调度）
   - 如何避免总线冲突（RS485 共享总线）
   - 如何做批量读取地址归并（减少请求次数）
   - 如何做周期自适应（某设备变慢时不拖垮整体）
4. SimulatedTransport 的设计（用于无硬件开发与单元测试）
5. 通信层可测试性的保证手段

请给出核心代码，并说明每个设计的现场理由。
```

### 2.3 并发模型设计

```
请设计这个上位机项目的并发模型。

场景参数：
- 采集设备数：{{n}}
- 采集周期：{{ms}}
- 单标签数：{{n}}
- 界面刷新率：{{Hz}}
- 数据落库频率：{{条/秒}}

1. 线程/任务分配表：每个线程的职责、优先级、生命周期、取消方式

   - 用什么方式（BeginInvoke / SynchronizationContext / Timer 批量刷新）

5. 死锁风险的排查清单（针对本项目的具体位置）

7. 优雅停止流程：如何保证所有任务在 3 秒内退出

给出代码骨架，并说明每个选择在高频/低频、单设备/多设备下的差异。
```

```
- 设备：{{型号}}
- 接口：{{串口/TCP}}
- 协议：{{协议}}
- 现场环境：{{干扰源、线缆、距离}}
- 软件版本：{{}}

已有信息：
- 报文日志：{{粘贴关键报文}}
- 错误信息：{{粘贴异常或错误码}}
- 出现前的操作：{{}}
- 其他设备是否正常：{{}}

3. 给出排查顺序（从最可能、最容易验证的开始）
4. 说明如何区分"硬件问题 vs 软件问题 vs 配置问题"
```

### 4.2 性能问题排查

```
上位机出现性能问题，请帮我定位。

现象：
{{描述：界面卡顿 / CPU 高 / 内存持续增长 / 通信延迟 / 数据丢失}}

监控数据：
- CPU：{{%}}，高峰时 {{%}}
- 内存：{{起始 MB}} → {{当前 MB}}，{{时长}}
- 句柄数：{{起始}} → {{当前}}
- 线程数：{{}}
- GDI 对象：{{}}
- 通信错误率：{{}}
- 采集周期实际：{{ms}}（设计 {{ms}}）

场景参数：
- 设备数：{{}}，标签数：{{}}
- 采集周期：{{ms}}
- 界面刷新：{{Hz}}，曲线通道：{{}}
- 数据落库：{{条/秒}}

请：
1. 判断这是哪一类问题（内存泄漏 / 句柄泄漏 / CPU 密集 / IO 阻塞 / 锁竞争 / GC 压力）
2. 给出定位方法（用哪些工具、看哪些指标）
   - 内存：.NET CLR Memory 计数器、dotMemory、ANTS
   - CPU：PerfView、dotTrace、VS 性能探查器
   - 句柄：Process Explorer 对比两次快照
   - 卡顿：UI 线程阻塞检测
3. 按可能性列出根因，每个给出验证方法
4. 给出优化方案（按收益/成本排序）
5. 说明优化的风险（如降低精度、增加复杂度）
6. 给出优化后的预期指标与验证方法

特别注意这些上位机高频性能问题：
- UI 定时器里做了重活
- 高频事件直接刷新控件而不是批量
- 曲线控件每点重绘
- 每次通信 new 大量对象（GC 压力）
- 字符串拼接打日志（高频）
- 未复用缓冲
- lock 范围过大包住 IO
- 数据库逐条提交
```

### 4.3 崩溃问题排查


## 通用提示词

### 代码评审

```
请以资深上位机工程师视角评审以下代码。

代码：
{{粘贴}}

请按以下维度评审，每个问题给出：严重程度（致命/严重/一般/优化）、问题描述、
为什么是问题（结合工控现场）、修复建议、修复代码。

评审维度：
1. 正确性：逻辑是否正确，边界条件是否处理
2. 并发安全：是否有竞态、死锁、跨线程访问
3. 资源管理：IDisposable 释放、事件取消订阅、句柄泄漏
4. 异常处理：是否吞异常、是否区分可重试/不可重试
5. 性能：是否有不必要的分配、GC 压力、锁竞争、UI 阻塞
6. 可维护性：命名、注释、硬编码、配置外置
7. 可测试性：是否可 Mock、是否有副作用
8. 现场适应性：日志充分性、故障隔离、自恢复能力
9. 安全：写操作的校验与确认、权限、危险指令防护

最后给出：
- 必须修复项清单（按优先级）
- 建议优化项清单
- 整体评价与主要风险
```

### 现场问题快速响应

```
现场出问题了，情况紧急，请快速给方案。

现场情况：{{设备、环境、当前状态}}
可用时间：{{能停机多久}}
已有信息：{{日志、报错}}

1. 【立即规避】（1 分钟内可执行的操作，让现场先恢复）
2. 【快速判断】（30 分钟内可以确认的排查方向，按可能性排序）
3. 【根本解决】（原因与彻底修复方案）
4. 【防复发】（同类问题的预防措施）

优先给"能让现场先动起来"的方案，不要一上来就要求重启或停机。
```

## 使用技巧

| 技巧 | 说明 |
|---|---|
| 分段投喂 | 大型项目按阶段使用对应提示词，不要一次要求生成全部 |
| 带上下文 | 每次对话带上角色设定 + 当前项目状态摘要 |
| 要求确认 | 明确要求 AI"信息不足时先提问，不要假设"，避免编造寄存器地址 |
| 要求理由 | 要求"每个决策给出理由和备选方案"，便于后续追溯 |
| 要求坑点 | 明确要求"指出该方案在现场可能踩的坑"，这是资深与初级的核心差异 |
| 索要验证 | 要求"给出验证方法"，避免方案正确但无法证明 |
| 迭代收窄 | 先要架构，确认后要接口，再确认后要实现，避免一次性生成大量未审代码 |
