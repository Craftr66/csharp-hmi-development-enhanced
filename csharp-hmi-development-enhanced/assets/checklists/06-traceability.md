# 追溯与版本核对表

> 上位机软件在现场往往存在"多个版本、多台设备、多个工位"的情况。
> 缺乏追溯会导致：现场问题无法复现、升级后协议不匹配、无法定位是哪版软件的缺陷。

---

## 第一部分：软件版本管理

### 1.1 版本号规范

建议采用 `主版本.次版本.修订号.构建号`，如 `2.3.1.1456`：

| 段 | 含义 | 变更规则 |
|---|---|---|
| 主版本 | 架构级变更、不兼容升级 | 协议不兼容、数据库结构变更 |
| 次版本 | 功能新增 | 新增功能，向后兼容 |
| 修订号 | 缺陷修复 | Bug 修复，无功能变更 |
| 构建号 | 自动递增（CI） | 每次编译 |

- [ ] 版本号在项目属性中统一维护（`AssemblyInfo.cs` 或 `Version.props`）
- [ ] 版本号在程序标题栏/关于对话框可见
- [ ] 版本号写入日志文件头
- [ ] 版本号写入数据库（便于判断数据来自哪个版本）
- [ ] 版本号与 Git tag 一致

### 1.2 版本清单

| 版本号 | 发布日期 | 变更摘要 | 协议版本 | 数据库版本 | 适用设备固件 | 状态 |
|---|---|---|---|---|---|---|
| | | | | | | ☐发布 ☐测试 ☐停用 |

### 1.3 分支策略（Git）

```
main / master          稳定发布分支（对应现场版本）
  ├── release/x.y      发布准备
  ├── develop          开发主干
  │     ├── feature/xxx
  │     └── bugfix/xxx
  └── hotfix/xxx       现场紧急修复
```

- [ ] 分支策略已定义并遵守
- [ ] 现场问题修复走 hotfix 分支并合并回主干
- [ ] 每个现场版本有对应 tag
- [ ] 提交信息规范（feat/fix/docs/refactor）

| | 协议 v1.0 | 固件 v1.0~v1.2 | ✅ 兼容 | |
| | 协议 v1.1 | 固件 v1.3+ | ✅ 兼容 | 新增命令码 0x05 |
| | 协议 v1.0 | 固件 v1.3+ | ⚠️ 不兼容 | 需升级软件 |

## 第五部分：生产数据追溯

### 5.1 数据关联关系

```
产品序列号 (SN)
   ├── 测试记录 (TestRecord)
   │     ├── 软件版本
   │     ├── 上位机编号
   │     ├── 仪器序列号
   │     ├── 测试时间
   │     └── 各测试项原始数据
   ├── 操作员
   └── 测试结果（合格/不合格）
```

- [ ] 产品序列号唯一且可靠采集
- [ ] 每条记录含软件版本
- [ ] 每条记录含仪器序列号
- [ ] 每条记录含操作员
- [ ] 每条记录含时间戳（来源明确）
- [ ] 原始数据保留（不仅保存处理后的判定值）
- [ ] 数据不可篡改（只追加，或有审计日志）
- [ ] 数据保留期符合客户/行业要求（___ 年）

> 用这三个问题检验追溯体系是否有效：

1. **现场报"数据不对"，我能否在 30 分钟内确定：是哪个软件版本、哪台仪器、哪个配置、哪个操作员产生的？**
   ☐ 能 ☐ 不能 → 缺失环节：______

2. **下位机升级了固件，我能否确定哪些上位机版本会不兼容？**
   ☐ 能 ☐ 不能 → 缺失环节：______

3. **某个缺陷影响数据正确性，我能否查出哪些已交付数据受影响？**
   ☐ 能 ☐ 不能 → 缺失环节：______
